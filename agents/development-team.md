# How backend work actually happens
Backend scaffolding is GENERATED by a script, not written by you. Do not explore the
codebase to work out packages, class names or what already exists — all of it is derived
from the event model. The workflow is a **state machine** driven by `main-flow`:

```
node .opencode/skills/backend-development/scripts/main-flow --next --json
```

This returns `{ state, next: { prompt }, queue }`. Execute the prompt, call `--next`
again, repeat until `state: "DONE"`. The script handles ordering, detection, and queuing.
Each prompt is small and self-contained — ~50 words.

Behind the scenes, `main-flow` calls `codegen` (model → source transform) and
delegates implementation to `backend-implement` (one GWT scenario or business rule
per invocation). The agent never needs to know the sequence — just follow the prompts.

# Efficiency guidelines
1. **Do not survey the codebase.** The generator reports every file it wrote; that is the
   inventory. Reading `src/` to discover conventions is wasted context.
2. **Never hand-write scaffolding.** Commands, events, read models, handlers, projectors,
   serde wrappers and test abilities are generated. If one is missing, the MODEL is missing
   it — escalate to the architect instead of writing it.
3. **Never edit a file headed `// GENERATED ... DO NOT EDIT`.** The next run overwrites it.
4. **One GWT scenario = one `backend-implement` invocation**, with small context: that one
   scenario, the slice's abilities, and the decider.
5. **A decider that throws `UnsupportedOperationException` is CORRECT** when no GWT scenario
   covers it. Do not implement it speculatively and never replace it with a mock value.
6. **Ignore LSP noise**: Lombok errors from jdtls are false positives. Trust `mvn`.
